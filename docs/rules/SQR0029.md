# SQR0029 - Do not call non-readonly struct members through readonly variables

<!-- sources -->
Sources: [DefensiveStructCopyAnalyzer.cs](../../src/squirix.analyzers/DefensiveStructCopyAnalyzer.cs),
[StructSizeEstimator.cs](../../src/squirix.analyzers/StructSizeEstimator.cs)
<!-- sources -->

A struct member that is not marked `readonly` may mutate the struct. The compiler cannot allow that through a
variable it must keep unchanged, so it copies the struct and runs the member on the copy. The copy costs time for a
large struct, and whatever the member changes is silently lost: a counter in a `readonly` field never advances, an
enumerator never moves.

The rule reports a method call, property read or indexer read whose member is declared on a struct, is not
`readonly`, and whose receiver is one of:

- a `readonly` field, instance or static;
- a `ref readonly` field;
- an `in` or `ref readonly` parameter;
- a `ref readonly` local;
- the result of a method, property or indexer that returns by `ref readonly`;
- an element of an inline array held by one of the above (`_items[0].Next()` with a `readonly` inline-array field);
- a ref conditional with at least one branch from the above (`(first ? ref a : ref b).Next()` with an `in`
  parameter): the compiler treats the whole expression as readonly, whichever branch is taken;
- a field of a struct that is itself reached through one of the above, including a field read inside a `readonly`
  member of its struct.

A readonly field is still writable while its own object is being initialized, and no copy is made there: in a
constructor, an `init` accessor or a field or property initializer of the declaring type, on the instance being
initialized. A lambda or local function inside a constructor does not count, and neither does a field of another
instance.

For a ref field only the kind of reference matters. A `ref readonly` field is always reported, in a constructor too,
because the struct behind it cannot be changed through it. A `ref` field is never reported, even when declared
`readonly ref`, read inside a `readonly` member or reached through a readonly variable: `readonly` there only fixes
where the reference points, and the member runs on the original struct. A `readonly` field of that struct is still
reported.

Nothing is reported for members of a `readonly struct`, for `readonly` members, for members inherited from
`System.ValueType` or `System.Object`, for writable receivers (locals, by-value and `ref` parameters, non-readonly
fields other than `ref readonly` ones), for temporary values and inside `nameof`. A non-readonly member called on
`this` inside a `readonly` member is left to the compiler warning CS8656.

Not analyzed: calls the compiler makes implicitly (`foreach`, `using`, deconstruction), events, and interface
members called on a type parameter, where the copy depends on the type argument.

Fix the member by marking it `readonly` when it does not mutate; when it has to mutate, make the variable writable
or copy the value to a local explicitly.

By default every struct is reported, because the lost mutation is a defect at any size. Framework structs whose
members are not marked `readonly`, such as `ValueTuple`, `HashCode`, `SpinLock` and collection enumerators, are
reported too. The `SQR0029.min_struct_size` `.editorconfig` option (default 1) limits the rule to structs of at
least that many bytes, for code bases that only care about the cost of the copy; a struct whose size cannot be
estimated is then skipped.

```csharp
struct Counter
{
    private int _count;

    public int Next() => ++_count;
}

// non-compliant: Next runs on a copy, so the counter never advances
private readonly Counter _counter;

int Take() => _counter.Next();

// compliant
private Counter _counter;

int Take() => _counter.Next();
```

Severity: **Warning**.

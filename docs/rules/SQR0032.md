# SQR0032 - Do not convert a `Task<T>` to `Task` in a delegate return

<!-- sources -->
Sources: [DiscardedTaskResultDelegateAnalyzer.cs](../../src/squirix.analyzers/DiscardedTaskResultDelegateAnalyzer.cs)
<!-- sources -->

`Task<T>` converts implicitly to `Task`. When a lambda, anonymous method or method group returns `Task<T>` but the
delegate it is converted to returns `Task`, the `T` result is silently lost, and so is any value the caller needed.
The compiler reports this for async lambdas (`CS8031`), but not for non-async lambdas and not for method groups.

The rule reports:

- a non-async lambda or anonymous method converted to a delegate whose return type is `Task`, at each returned
  expression of type `Task<T>`: `Func<Task> f = () => GetAsync();`, a custom `delegate Task FooAsync();`, or a lambda
  argument for which overload resolution picked a `Func<Task>` parameter;
- a method group whose method returns `Task<T>`, converted to such a delegate (`Func<Task> f = GetAsync;`, including
  a local function used as a method group), at the method group expression;
- each arm of a conditional or switch expression body whose type is `Task<T>` and is converted to `Task`
  (`() => b ? GetAsync() : Task.CompletedTask`), at the offending arm;
- a delegate created from another delegate whose return type is `Task<T>` (`new Func<Task>(funcOfTaskInt)`);
- a returned type that derives from `Task<T>`.

Assertion helpers such as `Func<Task> act = () => sut.GetAsync();` are reported by design: the result is lost to the
helper too. Fix them by declaring `Func<Task<T>>` or by an explicit `(Task)` cast.

Fixes:

- use a delegate that returns `Task<T>` (`Func<Task<T>>`) when the result matters;
- make the discard explicit with `async () => _ = await GetAsync()`, or with a cast, `() => (Task)GetAsync()`.

## What is not reported

- async lambdas and async anonymous methods, which the compiler already checks;
- delegates that return `Task<T>`, and returned values already typed `Task`;
- `Task<T>` where `T` is itself `Task`, `Task<U>`, `ValueTask` or `ValueTask<U>`: nested tasks are a different problem;
- explicit casts such as `(Task)GetAsync()`, which state the intent;
- APIs where overload resolution chose a `Func<Task<T>>` overload, such as `Task.Run(() => GetAsync())`;
- local function declarations, unless the local function is used as a method group;
- `ValueTask<T>`, which has no implicit conversion to `ValueTask`.

```csharp
static Task<int> GetAsync() => Task.FromResult(1);

// non-compliant
Func<Task> run = () => GetAsync();
Func<Task> group = GetAsync;

// compliant
Func<Task<int>> run = () => GetAsync();
Func<Task> discard = async () => _ = await GetAsync();
```

Severity: **Warning**.
